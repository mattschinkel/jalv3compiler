## Problem Statement

The user's goal: "mainly for now we want to look at improving the IR and the allocator that was added/updated recently."

Concretely, the indirect emitter classifies how a value is reached (`pic_access_kind_t`: DIRECT, RESOLVE, LINEAR, WALK_BAKED, WALK_RUNTIME, FAT, REFUSE) inside `pic_access_plan_get()` / `pic_access_plan_fill_var()` (`src/libpic12/pic_op_indirect.c:306-430`). It derives that classification at emit time from variable flags, variable definitions, allocator-provided object views, the chunk map and the fat-object registry. The enum has **no behavioural consumer**: it is written and printed by the audit, while emitter decision code reads the plan's fields 60 times across four emitter files. There are 13 external plan computation call sites (14 including the internal call inside `pic_access_plan_get()`): `pic_op_ptr.c:48,212,427,510`; `pic_op_assign.c:587,912,920,928`; `pic_op_fsr.c:374,1088,1197`; `pic_op_indirect.c:661,888`. The access fact is re-derived per emitter instead of carried once, and the emitter itself decides what to do with it.

The diagnosis chosen in the session: **the IR drops access facts and the allocator re-derives them.** The chosen remedy goes one step further than caching: the access decision moves out of emitter code and into data.

Inventory rule (reproducible): references to `plan`/`dplan`/`wplan` fields in `pic_op_assign.c`, `pic_op_fsr.c`, `pic_op_indirect.c` and `pic_op_ptr.c`, excluding the two plan constructors (`pic_access_plan_fill_var`, `pic_access_plan_get`) and the consistency checker, including the setup audit print. Reproduced by `.gstack/tmp/measure-plan-reads.py`: `aop` 17, `bind_walk` 8, `runtime_map` 7, `ptr_lookup` 5, `value_map` 5, `ptr_read_call` 4, `holed` 4, `sv_view` 3, `chunked` 2, `fat_candidate` 3, `slot_pointee_array` 1, `kind` 1 = **60**. Direct `VARIABLE_FLAG_PTR_*` reads: **9 total**, of which 4 are the constructor's reads in `pic_access_plan_fill_var` (`pic_op_indirect.c:324-328`) and 5 are emitter-decision reads in `pic_op_bank.c` (3) and `pic_op_ptr.c` (2). `pic_op_assign.c` has only a comment and no read.

## What Makes This Cool

The plan becomes the compiler's public, checkable artifact: **plan is data, the emitter is an interpreter.** A per-target recipe table maps a kind to an ordered list of steps (bank setup, chunk walk, pointer load, offset add). Emitters stop deciding and become a dispatch over recipes, so the hot path has zero boolean reads and every memory access the compiler emits is explainable as a table row.

Three things make it checkable rather than aspirational:

- A generated **kind × site matrix**: instrument each emit site once, record which facts it reads per value, and derive the recipe vocabulary from the matrix. The matrix is the design document and the migration checklist.
- A **`--dump-plan` gate**: plan and recipe diffs become the primary assertion on the sample corpus; gpsim/QEMU then confirm the selected recipe executes.
- The **kind is stored once on the IR value** per layout generation, so emitters and the gates read the same key.

The payoff is subtraction: converted emitter families lose their decision logic, and parallel accessors are deleted rather than wrapped.

## Constraints

- Strict C89: declarations at block top, no `//`, built with `-ansi -pedantic -Werror -Wall -Wshadow`. Recipe tables must be static const data plus function pointers; no dynamic allocation.
- Placement is final only at `code_gen_pass == 2`; layout trials run before and create scratch belonging to layouts that are thrown away.
- `libcore` must not learn bank, chunk or fat-tag semantics: PIC32 and ESP32 share it.
- Every codegen change needs a gpsim/QEMU runtime witness and a fix document under `fixes/`.
- `bin/beta/jalv3-x86-64` and `.exe` are tracked; a build that updates them commits them.
- `src/libpic12/pic_var.c` is about 5,500 lines and is **out of scope for layout changes**; this design reads its object-view and chunk-map accessors (Settled Decisions #10). When an existing helper or emitter pattern already does a step, reuse it; do not re-derive it in recipe form.

## Premises

1. **Per layout generation, once per value.** Emitters run in `code_gen_pass` 0, 1 and 2, and pass-2 layout trials emit before final placement (`pic.c:6362-6470`); placement also mutates after the trials (`pic_var_trial_install`, `pic_var_late_replace_all`, `pic_var_chunk_prepare_emit`, open-array formal blocking). The classification is therefore computed and stored once per value **per layout generation**, with a monotonic counter bumped on every one of those mutations and again when the winning layout is installed. Every consumer within a generation reads the stored value. The final installed generation is the canonical record the emitters read; the dump also records the earlier generations, and the gate compares the generation-id list. The front end cannot compute it: chunked/holed/fat depends on the layout. Mechanically, each stored record carries its generation id; a read whose id differs recomputes and overwrites, so no global value enumeration or clear hook is needed. A clone invalidates the record rather than copying it (A3); a variable remap clears it; the next read recomputes.
2. **The recipe key is `(kind, operation/site family, fact vector)` (A1).** Emitters dispatch on that key; `kind` alone is a priority summary. Variable-only sites (`pic_access_plan_fill_var`, used by the fsr and assign walk helpers) receive a variable-derived kind from the same enum: `runtime_map` -> WALK_RUNTIME; `holed`, `chunked` or `sv_view` -> WALK_BAKED; otherwise DIRECT. `bind_walk` and the pointer-storage facts are named recipe inputs, not kind values, so they are recipe sites too rather than an exception. Residual facts the recipe needs (likely `aop`, `slot_pointee_array` and the pointer-storage facts) are named recipe inputs, justified by the matrix, never ad-hoc branches in the emitter. No emitter in the four converted families reads raw `VARIABLE_FLAG_PTR_*`.
3. **Split the facts.** The target-independent kind rides the IR; bank/chunk/fat-tag predicates and the recipe contents stay in `libpic12`. `libcore` learns no bank semantics.
4. **Small steps, each proven.** Although the end state is a rewrite of emitter decision logic, it lands family by family: recorder first, then one recipe family per commit, each with a witness and a deletion. No big-bang sweep.

The office-hours cross-model review challenged none of these. The autoplan CEO review challenged the harm premise (F2), the epoch mechanism (F3, fixed by layout generations) and the safety of making `kind` the codegen key (F4, addressed by the always-available consistency audit and UC1).

## Cross-Model Perspective

- The subagent's weekend framing (recorder, gate, FAT family) is a suggestion, not this plan's estimate; this plan's effort is stated in Next Steps.
- It agreed with all four premises. Its caution was to treat the recipe-interpreter as a staged rewrite, not a single sweep.

## Approaches Considered

### Approach A: Plan cache + kind dispatch

Keep the model in `libpic12`, memoize the plan per value, migrate emitters to `switch(kind)`. No `libcore` change. Effort M, Completeness 6/10. Ruled out: the IR still drops the fact and other consumers cannot read the record.

### Approach B: IR-carried plan, computed once

Store the kind on the IR value; keep the detailed booleans in a `libpic12` side record; emitters read the stored kind but still decide in code. Effort L, Completeness 9/10. Ruled out as the endpoint, but its storage mechanism is retained: C needs the stored key and the IR half of the goal depends on it.

### Approach C: Plan-as-data recipe interpreter (chosen)

A per-target recipe table keyed by kind; emitters become a dispatch over recipes. Effort XL for the full arc (human ~5-6 weeks / CC ~1.5-2 weeks): FAT `L` (human ~2-3 weeks / CC ~1-2 days), then the other three families ~1 week human / ~2-3 days CC each. Completeness 10/10 as an **end-state target**, provisional 7/10 until the matrix closes the vocabulary. Chosen because it removes the decision logic itself, which is the deletion the session exists for, and because the stored kind plus the matrix makes the rewrite mechanical and witness-backed.

## Recommended Approach

**C, with B's storage: recipes indexed by a kind stored once on the IR value.**

Why:

- The recipe table is the complete form of "one model": the decision is data, not code repeated in each emitter.
- Storing the kind on the IR value keeps the original IR goal alive and gives every emitter the same key.
- The recorder and matrix answer the two questions that could sink C before any emitter changes: whether `kind` (plus named residuals) covers every site, and what the recipe vocabulary actually is.
- Staging by family satisfies premise 4 and gives a visible deletion at each step.

## Settled Decisions and the Research Gate

These were open in the office-hours draft. They are decided here; only the matrix vocabulary remains a research output.

1. **Layout generation, not pass/trial epochs.** A monotonic **layout-generation counter** is bumped on every operation that can change placement or the object view: trial install (`pic_var_trial_install`), late replace (`pic_var_late_replace_all`), chunk prepare (`pic_var_chunk_prepare_emit`), and open-array formal blocking. The winning layout is installed and bumped explicitly before final emission, so no emission reads a discarded trial's plan. Each stored record carries the generation id; a read with a different id recomputes and overwrites. `JALV2_NO_LAYOUT_TRIALS=1` is compared to a `win=0` run by the final generation's rows, not by generation-id lists (A10).
2. **Two stores, not one.** (a) The whole `pic_access_plan_t` is cached per value/generation in a `libpic12` side table keyed by value id; `access_kind` on `value_t` remains the portable public key (A2). (b) The recorder log is append-only, keyed by `(program path, generation id, site id, expression ordinal)`, and exists only to build the matrix and the dump. Conflating them would be a design error.
3. **Clone and remap.** `value_clone` marks the record invalid rather than copying it (A3). A variable remap clears it. The next read recomputes. No "leave unset" case.
4. **Recipe representation (C89), ids and the target seam.** One static const table per backend family of `{step_fn, unsigned arg}` entries. The classic table lives in `libpic12` (classic cores have no `pic_backend_t` descriptor); the descriptor field is reserved for future PIC32/ESP32 adoption (A5). Device differences travel in the context struct. A step that needs control flow emits branches inside its own function; recipes do not nest. Recipe ids are stable symbolic names (for example `fat.walk_banked`), unique and sorted lexically; they are never numeric indexes. The stored field is named `access_kind`; the dump key is `kind`. **Every dispatch has a fatal default:** a kind with no row logs `internal error: no access recipe for kind=%u site=%u generation=%lu`, installs no image, and exits non-zero. `JALV2_ACCESS_RECIPE_FAULT` injects that default for tests.
5. **Recipe vocabulary.** The expected closed set is bank setup, chunk walk, pointer load, offset add, read/write. The matrix confirms or extends it. A site needing a fact that `kind` cannot encode becomes a named recipe input, never an emitter branch.
6. **`aop` at 17 reads.** It is implied by `kind=RESOLVE` by construction; the matrix verifies that. It is not an independent residual at value sites. Variable-only sites have no `aop`.
7. **REFUSE.** `PIC_ACCESS_REFUSE` is diagnostic-only: its recipe emits no code and the compile fails with the diagnostic already logged. No fallback recipe. Any other kind with no table row is the fatal default in decision 4, never a silent empty recipe.
8. **Dump format, determinism and the gate failure contract.** Key: `(program path, generation id, site id, expression ordinal, kind, sorted named inputs, recipe id)`. `program path` is repo-relative, so duplicate basenames are distinguished. No `value_t` ids or addresses: value ids shift on any added value and would churn the baseline. One consolidated baseline file per suite under `unit-tests/plan-baselines/<suite>.txt`, named for the regression-suite glob it covers; lines sorted by the key. L1 diffs a pinned subset; L2 diffs the full corpus. The gate stores the sorted generation-id list and diffs the lists; a hash is only a fast equality check. On failure it prints the program path, generation id, changed-row counts, the first N added/removed/changed rows and the `.plan` path, with stable code `JAL-PLAN-DIFF`, side effects "compile output complete, baseline unchanged", and a fix line `unit-tests/run_gates.sh --level 1 --update-plan-baseline` preceded by "review the diff first"; retry bound 1. `--update-plan-baseline` writes a temp file in the same directory and renames it; on failure it exits non-zero naming the path and errno. Refresh order: intentional codegen change -> hex manifest -> plan baseline, both reviewed together.
9. **Witness split.** The recorder and `--dump-plan` assert the plans for passes 0/1 and each trial layout (compile-time). gpsim/QEMU validates only the final image's runtime behavior.
10. **Allocator scope.** `src/libpic12/pic_var.c` is **out of scope** for layout changes. This design reads its existing object-view and chunk-map accessors; the only new libpic12 storage is the access-record module. The user's "allocator" goal is met by making its object view the single source the emitters read, not by changing placement.
11. **Variable-only coverage.** The matrix covers the fsr and assign variable-only sites and tests `bind_walk`, `holed`, `chunked`, `sv_view`, `runtime_map` against the mapping in premise 2.
12. **Two stores, two failure policies, site ids.** The **dispatch-feeding store** (value record and variable-keyed record) is always fatal on allocation failure: `pfile_log_syserr(pf, ENOMEM)` plus the error count and a non-zero exit. The **recorder log** is an append-only growable array keyed by `(program path, generation id, site id, expression ordinal)`, initial capacity 4096, doubled on overflow; it may degrade only when recording is off, and when recording is on any lost record is fatal. Duplicate keys are detected per `(program, generation, key)` and reported with the count and both sources, not silently overwritten. `site id` is a stable string key `file:function:label` (A7), so line moves and renames do not churn the baseline; additions and removals print the key and distinguish an intentional registry change (`--update-plan-baseline`) from a collision (fix the key). Value sites use `access_kind` on `value_t`; the six variable-only external `fill_var` sites (`pic_op_fsr.c:374,1088,1197`, `pic_op_assign.c:912,920,928`) use a variable-keyed record. The internal `fill_var` call from `plan_get` is marked by a file-scope `in_plan_get` flag and writes only after `plan_get` completes.
13. **Enforcement and the toggle.** A stored-record/facts mismatch on the codegen key is **unconditionally fatal** via the internal-error convention: value/variable identity, site id, generation id, expected and actual fact, and the dump path. `JALV2_ACCESS_RECORD` only enables the redundant re-derivation audit and the recorder log; it never gates fatality. The toggle uses `pic_env_on()`: unset/empty/0/false/no/off are off; any other value is on. `JALV2_ACCESS_RECIPE_FAULT` and `JALV2_ACCESS_RECORD_FAULT` inject the fatal paths for tests, following `JALV2_ALLOC_AUDIT_FAULT`.
14. **Corpus and fixtures.** The corpus is the deterministic compiling classic-PIC programs in the regression suite (`sims/run_regression_suite.py` globs) plus the `demo_sample` pins; exclude fuzz/negative-input pins and PIC32/ESP32 targets. Clone and variable-remap fixtures live under `unit-tests/` and are named in the recorder step.
15. **Family coverage.** Converted families: `pic_op_indirect.c` (FAT first, then the remainder), `pic_op_ptr.c`, `pic_op_assign.c`, `pic_op_fsr.c`. `pic_op_bank.c` is **out of scope**: its 3 `PWIT_FLAG_IND` reads are temp materialization, not access-plan sites, and it never calls `plan_get`/`fill_var`. The zero-read metric applies to the four converted families (baseline 2, both in `pic_op_ptr.c`); bank's 3 reads and the 4 constructor reads remain.
16. **TODOS.md.** Create `TODOS.md` at the repo root in Step 1, add `!/TODOS.md` to `.gitignore` (the root allowlist otherwise ignores it), and commit both with the first change.
17. **Test file, exposure and link.** Recipe steps live in `src/libpic12/pic_access.c` + `.h` with non-static `_pic_recipe_*` functions. `unit-tests/test_access_recipes.c` links `libcore-x86-64.a`, `libpic12-x86-64.a` and `libutils-x86-64.a` with a minimal `pfile_t` stub, run by `unit-tests/test_access_recipes.sh`, following the `test_fat_tags.c` pattern. Tests cover the fatal no-recipe default, the unconditional mismatch, and both allocation-failure paths via the fault hooks.
18. **"Zero decision branches," defined.** A plan-field-dependent conditional in a converted emitter function. Counted two ways: the matrix shows every site's recipe is determined by `kind` plus named inputs only, and a grep gate over the converted emitter functions (excluding the constructors and consistency checker in `pic_op_indirect.c`) asserts zero `plan.`/`plan->` field reads.

### Eng amendments (F1-F20)

A1. **Recipe key is the full fact vector, not `kind` alone.** Key = `(kind, operation/site family, fact vector)`. The fact vector is enumerated up front: `aop`, `slot_pointee_array`, `chunked`, `holed`, `sv_view`, `runtime_map`, `value_map`, `bind_walk`, `ptr_lookup`, `ptr_read_call`. `kind` is a priority summary and drops facts below the winner; the matrix validates the vector but does not discover it.
A2. **Store the whole plan.** A `libpic12` side table caches the full `pic_access_plan_t` per value/generation keyed by value id; `access_kind` on `value_t` remains the portable public key. This is what lets the 13 sites read one record instead of re-deriving residuals.
A3. **Generation is a facts version.** Bump it on every mutator of any plan input: `pic_fat_object_register`, `pic_var_pointer_bind_escape`, the pass-boundary stash commits (`pic_var_use_stash_from_pass0`/`merge_pass1`), variable-definition changes, and value-flag mutations on clones. `value_clone` marks the copied record invalid rather than reusing it. The re-derivation audit runs in the plan gate, not only on demand.
A4. **The IR record is a pair.** `{access_kind, generation}` plus a validity flag; zero is a legal kind, so zeroing cannot mean unset. `value_variable_set`, `value_flag_set_all`, clone and remap clear it; accessors are specified in Step 3.
A5. **Classic table seam.** The classic recipe table lives in `libpic12` (classic cores have no `pic_backend_t` descriptor); the descriptor field is reserved for future PIC32/ESP32 adoption.
A6. **Metric scope.** The "zero decision branches" metric covers plan-field conditionals only. Drop the "hot path has zero boolean reads" and "every access is explainable as a table row" claims; the dump explains plan inputs, not the internals of a step.
A7. **Site keys are strings.** Stable `file:function:label` keys, no manual ordinal registry.
A8. **Split baselines.** Fact rows (kind + named inputs) are strict and must be identical across a migration; recipe rows are the intentionally updated set.
A9. **Recorder concurrency.** One log per compile (`pid`/program in the path) plus an explicit merge step, or serial recording; state the per-compile size bound.
A10. **Trial witness.** `JALV2_NO_LAYOUT_TRIALS=1` is compared to a `win=0` run by the final generation's rows, not by generation-id lists.
A11. **Test wiring.** Register `test_access_recipes.sh` in `run_compile_pin_tests.sh`; spike the link in Step 1a; define an ENOMEM injection hook; add duplicate-key and growth tests.
A12. **Matrix drift.** `--check-matrix` regenerates and diffs at L2; assert every recipe row is exercised; add a sample where `win=1` is selected.
A13. **REFUSE is defensive.** Unknown kinds use the fatal default; REFUSE is noted as defensive, not a reachable recipe row.
A14. **Direct re-derivation in fsr.** `pic_fsr0_add_dynamic_index` reads the object view after the plan; the grep metric either allows that documented case or is extended to call it.
A15. **Determinism details.** Normalize the program path to repo-relative; define how the expression ordinal is assigned; pin codegen-affecting env (`JALV2_FAT_POINTERS`, `JALV2_NO_LAYOUT_TRIALS`) in the gate.
A16. **Dump presence.** A missing `.plan` is a gate failure; an empty plan is a valid empty baseline; `VARIABLE_NONE`/`0` records are skipped.
A17. **Workspace process.** Add the new sources to the Makefile/object list, run `make -C src clean` after dep-graph changes, write a per-commit fix doc under `fixes/`, and run the mandatory `jaldbg.py cost`/`pin-check` pre-flight.
A18. **Duplicate rows.** Identical duplicate row = OK; differing duplicate row = fatal.
A19. **No stale image.** A fatal recipe error must leave no stale or partial `.hex`; "installs no image" is tested.
A20. **Step 4 gate.** Do not write the first recipe until A1-A4 are implemented and the recorder confirms the fact vector. If the vector or the store does not close, "stop at B" is an allowed outcome (UC1).

The remaining research gate: the matrix must exist before the first recipe is written. It is the assignment, not an open design question.

## Appendix: Runnable Interface

Compiler flags use the single-dash `opt_defs` form with a description; gate flags
use the double-dash script form. The dump records ids and facts, never environment
values.

```sh
make build
JALV2_ACCESS_RECORD=1 JALV2_ACCESS_RECORD_OUT=/tmp/plan.log \
  bin/beta/jalv3-x86-64 -s lib sims/<sample>.jal
python3 unit-tests/access_matrix.py --log /tmp/plan.log \
  --out unit-tests/plan-matrix/<sample>.md
bin/beta/jalv3-x86-64 -dump-plan=/tmp/<sample>.plan -s lib sims/<sample>.jal
unit-tests/run_gates.sh --level 1
unit-tests/run_gates.sh --level 1 --update-plan-baseline
unit-tests/test_access_recipes.sh
```

A failed plan diff prints `JAL-PLAN-DIFF`, the program, generation, changed-row
counts, the first rows, and the `.plan` path; the baseline is unchanged. Review the
diff before running `--update-plan-baseline`.

## Feature switches

Every `JALV2_*` feature switch follows ONE rule (DX F1): unset or empty means
the switch's **default**; `1`/`true`/`yes`/`on` mean **on**; `0`/`false`/
`no`/`off` mean **off** (case-insensitive, surrounding whitespace ignored).
Any other value is an error the compiler does not swallow: one stderr line
with the stable code `JALV2-SWITCH`, the accepted values, the effective
mode, and this anchor; the default is then used.  A rollback such as
`JALV2_FAT_POINTERS=0` therefore cannot silently mean "on".

| switch | default | meaning |
|---|---|---|
| `JALV2_FAT_POINTERS` | on | the fat-pointer engine; a program's `pragma target fat_pointers` wins over the env |
| `JALV2_FAT_FORCE` | off | test-only: force every chunked bind fat |
| `JALV2_FAT_PTR3` | (engine default: 3-byte) | 14H pointer-width override |
| `JALV2_NO_LAYOUT_TRIALS` | off (trials on) | disable the PIC18/14H layout trials |
| `JALV2_ACCESS_RECORD` / `_AUDIT` / `_COVERAGE` | off | the access recorder, audit and coverage report |

The fat-pointer engine is **on by default** since 2026-11-11.  Precedence per
compile is **pragma > env > default**: `pragma target fat_pointers
on|off|3byte|2byte` (the program's own switch) wins, then
`JALV2_FAT_POINTERS`, then on.  `JALV2_FAT_POINTERS=0` still restores the
classic representation exactly (the recorded HEX manifest is the rollback
baseline) and prints one `JALV2-NOTICE` per compile; that mode is
**deprecated and the switch is removed after one release**.  The per-program
opt-out is `pragma target fat_pointers off`, which does not print the notice.

`jalv3-x86-64 --features` (alias `-v`) prints the effective modes before
compiling, and surfaces any invalid-value warning; it exits after the report.
