## Problem Statement

A3 ("one placement policy") is done and reviewed: every memory class routes
through `pic_mem_place()` with a request/result split, gated byte-identical.
The next rung the user chose is A7 from
`docs/investigations/unified_allocator_20261108.md` — "one report": the
allocator can describe itself (objects, segments, owned objects, violations,
capacity) and the report reads only the model.

Reading the current code, "always-on audit + capacity report" is already
half-landed:

- The invariant CHECK is already always-on (U4-1): `pic_var_segment_audit`
  (`pic_var.c:5634`) runs on every compile at the end of
  `pic_var_chunk_prepare_emit`, and a violation logs a WARN (`pic_var.c:5807`).
- The verbose audit line (objects/segments/owned/violations plus data/shared
  used/free/largest) already exists behind `JALV2_ALLOC_AUDIT`
  (`pic_var.c:5813`).

Three pieces remain for A7 to be true rather than approximately true:

1. `pic_blist_info_log` (`pic_var.c:6136`) is an empty stub. It is called at
   `pic.c:3419` — the successful-compile usage site, right next to the
   "code used" INFO line — and it says nothing today. This is where the data
   report should live.
2. The always-on violation verdict is a WARN, not the internal error U4
   specifies ("a violation is an internal error"). A warning can scroll past;
   an internal error cannot.
3. The coverage check re-derives the storage need from the variable
   (`pic_variable_storage_need_get`, `pic_var.c:5737`) instead of reading the
   object view — the one variable-fact read left in the audit, and the one
   place A7's "reads only the model" is not literally true.

## What Makes This Cool

A compiler that can answer "what did you place, where, and why" from one model
is the difference between a facade and a first-class subsystem. Today, after a
successful compile, the user sees "code used N of M words" but nothing about
data. Finishing A7 means the allocator reports its own usage the way code
does, and a placement invariant that breaks stops the build instead of
whispering a warning. The allocator becomes a citizen of the compile, not a
service.

## Constraints

- Strict C89 (`-ansi -pedantic -Werror -Wall -Wshadow`).
- A8 byte-identity: default builds stay byte-identical (HEX manifest 0 drift);
  the report is additive console output, not image output.
- No new representation. A7 is report-side; A6 capacity pins and the
  `alloc_capacity` table already landed in P3b and are out of scope.
- The report reads only the map (`pic_mem_map_t`) and the object view
  (`pic_mem_object_t`), not the variable list.

## Premises

1. A7 is report-side only. A6 (capacity pins) landed in P3b and is not in
   scope.
2. The invariant check is already always-on; the remaining work is the report
   surface, the verdict level, and one model-purity seam.
3. The coverage check's variable read is the last place the audit reads a
   variable fact; A7 is finished when it reads only the model.
4. A violation of the placement invariants is a real placement bug. The corpus
   is 2940 audited / 0 violations, so promoting it to an error is safe today
   and correct forever.

## Approaches Considered

### Approach A: Fill the report, keep the WARN

Fill `pic_blist_info_log` with the data usage report at INFO (mirroring "code
used"), leave the violation verdict as a WARN. Smallest diff; the report
appears, but a placement corruption still only warns.

### Approach B: A + promote the violation to an internal error (chosen)

Fill the report, and promote the always-on verdict from WARN to ERR so an
invariant violation fails the compile. This is U4's literal spec and what
makes the audit load-bearing.

### Approach C: B + close the coverage-need read

Also replace `pic_variable_storage_need_get` in the coverage check with the
object view's `size`, so the audit reads only the model. Most complete A7, but
it changes an input to a safety check and must first prove `obj.size` equals
storage need for every non-bit object the audit sees.

## Recommended Approach

**B.** Fill `pic_blist_info_log` (the report surface) and promote the
violation verdict to an internal error (the load-bearing audit). Each lands
byte-identical. Piece 3 (the coverage-need read) stays a documented follow-up:
it is a model-purity cleanup, not a missing capability, and it must not
silently change what the coverage check compares.

## Open Questions

- **Surfacing level.** The report site (`pic.c:3419`) logs "code used" at
  INFO; the data report should match. But any pin that compares compile stderr
  verbatim must be refreshed. Verify no gate compares stderr before choosing
  INFO over DEBUG.
- **Coverage-need purity (piece 3).** Does `pic_mem_object_get().size` equal
  `pic_variable_storage_need_get` for every non-bit object the audit sees? If
  provably equal, close the read; if not, leave it and document the exception
  in the audit comment.

## Success Criteria

- `pic_blist_info_log` prints data used/free/largest per region (data plus
  shared), reading only `pic_var.map`; the line appears next to "code used" on
  a successful compile.
- A placement-invariant violation logs an error (non-zero error count) instead
  of a warning; the corpus sweep reports 0 violations and
  `JALV2_ALLOC_AUDIT_SELFTEST` still proves the checker fires.
- L2 HEX manifest 0 drift; the `alloc_capacity` pin passes unchanged and
  `alloc_segment_audit` arm 7 is updated to expect the error verdict (its
  fault-injection arm flips from an exit-0 warning to a non-zero error).

## Distribution Plan

No new distribution: lands as a compiler-source commit. A build that updates
`bin/beta/jalv3-x86-64` commits that binary with the change.

### R2-1 — consistency (minor)

### R2-3 — clarity (minor)

**Problem**

> Open Question 1 warns about any pin that compares compile stderr verbatim, but the report site's code-used line and the WARN/ERR verdict are emitted by pfile_log, which writes to stdout (dst = pf->f_log ? pf->f_log : stdout in pfile.c), not stderr; only the JALV2_ALLOC_AUDIT verbose line uses fprintf(stderr, ...). The stated risk is attached to the wrong stream, and the question frames the level as undecided (before choosing INFO over DEBUG) although the Recommended Approach already commits to INFO.

**Remedy**

> Reword the open question to refer to pins/gates that compare merged compiler log output (stdout+stderr, as the pin scripts capture with >log 2>&1); state the level as committed to INFO with the gate verifying no output-comparing pin breaks.

### R2-4 — clarity (minor)

**Problem**

**Remedy**

> Correct the citation to pic_var.c:5808.

### R2-5 — clarity (minor)

**Problem**

> Premise 4 says promoting the verdict is safe today and correct forever, but the investigation doc the design itself cites records that the audit already produced one false invariant (the PIC_CHUNK_MAP_MAX segment-count check) that fired on a legitimate 11-segment word[400]. Correct forever assumes no future false positive; under ERR a false positive becomes a hard failure (non-zero exit and the .hex/.asm are deleted), not a warning.

**Remedy**

> Qualify the claim: acknowledge the false-invariant precedent and state that ERR promotion turns any residual false positive into a hard compile failure, mitigated by the full-corpus sweep gate, the selftest pin, and the containment/geometry checks; drop or soften correct forever.

### R2-6 — clarity (minor)

**Problem**

> Step 2's revised Gate line dropped the alloc_segment_audit pin without replacing it with the updated pin. The updated arm 7 (non-zero exit plus an error-level placement invariant violation under JALV2_ALLOC_AUDIT_FAULT=1) is the only gate that verifies the WARN-to-ERR flip this step introduces: the corpus sweep exercises zero real violations and JALV2_ALLOC_AUDIT_SELFTEST exercises a separate selftest code path, so neither covers the fault-injection verdict.

**Remedy**

> Restate the gate to require the updated alloc_segment_audit pin passing, e.g. full corpus 0 violations, plus JALV2_ALLOC_AUDIT_SELFTEST and the updated alloc_segment_audit pin.
